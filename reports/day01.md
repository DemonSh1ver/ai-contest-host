## 二、课题与使用场景

**课题及选用理由：** 本课题为「算法竞赛 AI 智能主持人」，针对算法竞赛赛后"滚榜播报"环节中人工念榜耗时、易错、节奏不一的痛点，用程序自动完成"读榜 → 生成主持词 → 语音播报"全流程，以营造竞赛滚榜的紧张感与氛围感。

**主要使用者 / 使用场景：** 算法竞赛赛事组织者与主持人，在比赛结束后将排行榜 JSON 导入程序，一键启动即可自动滚榜播报，替代人工逐队念榜。

**课内交付边界：** 课内环境无专有真机与外设，故以"标准台式机 + 系统自带中文 TTS 语音引擎（离线）"为交付边界，仅交付命令行程序，不依赖联网 API、GPU 算力或外部音频设备；核心链路（解析、主持词生成、滚榜排序、TTS 播报）均可在课内环境完整运行与演示。

**滚榜过程描述：** 比赛结束后，主办方将排行榜导出为 JSON 文件放入程序目录，一键启动后程序按名次从后往前逐队揭晓，主持人用饱含悬念的语气报出队名与成绩，配合"请看大屏幕""把掌声送给 XX 队"等话术调动现场，最终揭晓冠军、完成整场播报。

## 五、当日主题必写块：必做 / 不做 / 验收说法 / 风险

### 1. 必做（Must，9 天内必须完成的最小功能）

| 必做项 | 计划工期 |
| --- | --- |
| 读取排行榜 JSON 数据 | 第 2 天 |
| 解析排名与队伍信息 | 第 2 天 |
| 按滚榜顺序生成中文主持词 | 第 3 天 |
| 将主持词转为语音（TTS） | 第 4 天 |
| 播放语音 | 第 4 天 |
| 全链路贯通与演示 | 第 5 天 |
| 容错加固与验收准备 | 第 6~9 天 |

以上七项构成 9 天内必须交付的最小功能集，只覆盖"单机命令行读榜 → 滚榜播报"这一条链路，排期不超出 9 天。

### 2. 不做（Won't，本次明确不做）

- Web 界面 / 网页：仅命令行工具，无浏览器交互
- 数据库持久化：榜单文件即数据源，不建库
- 多人实时联机：单机运行，不支持多端同步
- 账号登录系统：本地工具，无用户体系
- 计分 / 排名计算：只读现成排行榜，不做分数运算

不做项均在 9 天工期外，保证范围可控、如期交付。

### 3. 验收说法（Acceptance）

**验收步骤：**

放入 JSON → 启动程序 → 听到 TTS 按滚榜顺序播放主持词。

**用户故事：**

- 作为**竞赛主持人**，希望程序能读取排行榜 JSON 并自动播报名次，以便**省去逐队人工念榜的时间**。
- 作为**参赛选手**，希望听到清晰的中文语音播报自己的排名，以便**第一时间确认自己的成绩**。
- 作为**赛事组织者**，希望播报流程一键启动、无需人工干预，以便**保证每场播报节奏一致、不依赖主持人临场发挥**。

**验收句：**

1. 放入排行榜 JSON 并启动程序后，主持人能直接听到完整的中文播报，无需逐队人工念榜。
2. 参赛选手在播报中能清晰听清自己队伍的排名与成绩。
3. 赛事组织者只需一次启动，程序即自动完成"读榜 → 生成主持词 → 语音播放"全流程，全程无需手动介入。

### 4. 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| TTS 引擎选型 | 不同引擎的中文语音质量、稳定性差异大 | 第 2 天技术选型时逐个做最小 demo 验证 |
| 中文读音不准 | 队伍名、人名、数字读法易读错 | 主持词生成时做数字转中文、特殊队名读音映射 |
| 榜单格式不固定 | 真实排行榜 JSON 字段可能与预设不一致 | 解析层做字段兼容与默认值，准备样例文件 |

## 八、AI 沟通

本课程鼓励使用 AI 助手，本节记录与助手协作的情况。

**不成功的沟通：**

- 直接让助手"照搬完整系统"时，助手倾向于生成大而全的代码与文档，边界不清、难以在 9 天工期落地；后来改为明确"只做单机命令行读榜播报的最小集"并列出「不做」清单，输出才聚焦到可交付范围。

**比较有效的沟通：**

- 用"必做与不做分列、且符合 9 天工期"作为约束提问，助手据此把必做项排进第 2~9 天的表格并给出工期边界说明，结果可直接采用。
