## 二、今日目标

第 1 天已经确定项目的最小主路径，第 2 天完成了模块划分和技术选型。今天继续完成 Day 2 遗留的 `parser → roll → script` 接口核对，重点不是继续增加外围功能，而是把主路径上的数据对象、模块接口、成功与失败情况以及后续实现边界固定下来，确保后续开发可以按同一套约定继续进行。

当前主路径为：


在梳理过程中发现，如果滚榜模块只按照最终排行榜从最后一名倒序到第一名，虽然能够满足第 1 天确定的 MVP，但实际演示时更接近"倒序念榜"，没有充分体现算法竞赛滚榜过程中"成绩解冻、排名变化和现场悬念"的特点。

因此，今天在不破坏原有 MVP 主路径的前提下，进一步预留了增强版滚榜所需要的数据和接口。后续可以在此基础上实现简化 ICPC 风格的滚榜过程，并根据排名变化生成不同情境的主持词。

需要明确的是：真实滚榜属于 MVP 之外的特色增强，不改变第 1 天确定的验收边界与最小功能集。

## 三、主路径上的数据或对象

本节只保留支撑主路径和后续滚榜增强的关键对象，不展开用户、权限、数据库等与当前课题无直接关系的设计。

| 数据对象          | 主要字段                                                        | 用途                                     |
| ------------- | ----------------------------------------------------------- | -------------------------------------- |
| `Team`        | `rank`、`name`、`solved`、`penalty`                            | 表示一支参赛队伍，是当前榜单和主持词逐队播报的基本单位            |
| `Submission`  | `team`、`problem_id`、`status`、`submit_time`、`wrong_attempts` | 表示一条题目提交记录，为后续实现隐藏提交解冻和成绩重新计算提供数据      |
| `Leaderboard` | `contest_name`、`round_no`、`teams`                           | 表示一场比赛的排行榜，是 `parser` 的主要产出            |
| `RollStep`    | `step`、`revealed_team`、`ranking`，后续扩展旧排名、新排名及成绩变化           | 表示一次滚榜揭晓，是 `roll` 和 `script` 之间的主要交接对象 |
| 主持词文本         | `str`                                                       | `script` 生成的中文文本，逐句组织，最终交给 TTS 播放      |

当前已有代码中的 `Team`、`Leaderboard`、`RollStep` 仍保持原有结构，用于保证 Day 1、Day 2 确定的 MVP 可以继续运行。

同时，为 Day 4 以后增强真实滚榜，暂时确定 `Submission` 数据以及 `RollStep` 的扩展方向。后续扩展重点包括：

```text
old_rank
new_rank
old_solved
new_solved
old_penalty
new_penalty
events
```

这些字段用于描述一次揭晓前后的状态变化，为"排名上升""反超""大幅跃升""进入前三""冠军揭晓"等事件判断提供依据。

## 四、调用约定

当前主路径采用单向数据流，上一步的输出作为下一步输入：

```text
JSON
  ↓
parse_leaderboard_file(path)
  ↓
Leaderboard
  ↓
reveal_order(teams)
  ↓
List[RollStep]
  ↓
generate_roll_script(lb, steps)
  ↓
中文主持词 str
  ↓
init_engine() / speak(engine, text)
  ↓
TTS 播放
```

根据当前代码，主要接口约定如下：

| 函数                                      | 输入                             | 输出               | 作用                    |
| --------------------------------------- | ------------------------------ | ---------------- | --------------------- |
| `parse_leaderboard_file(path)`          | JSON 文件路径                      | `Leaderboard`    | 读取并解析排行榜              |
| `reveal_order(teams)`                   | `List[Team]`                   | `List[RollStep]` | 按当前排行榜从最后一名到第一名生成揭晓步骤 |
| `generate_script(lb)`                   | `Leaderboard`                  | 中文 `str`         | 普通模式生成主持词             |
| `generate_roll_script(lb, steps)`       | `Leaderboard`、`List[RollStep]` | 中文 `str`         | 根据滚榜步骤生成主持词           |
| `init_engine()` / `speak(engine, text)` | 无 / 中文 `str`                   | TTS 引擎 / 播放      | 完成语音播报                |

### 成功一例

输入 `data/sample_leaderboard.json`，榜单包含 4 支队伍。

程序执行：

```text
parse_leaderboard_file
→ 得到 4 支队伍的 Leaderboard
→ reveal_order
→ 得到 4 个 RollStep
→ 揭晓顺序：摸鱼队 → 红名大神 → 不会就选C → AC 冲鸭
→ generate_roll_script
→ 生成中文滚榜主持词
```

输出中能够出现类似：

> "第四名，摸鱼队，解出三题。"

以及：

> "第一名，AC 冲鸭，解出五题。"

说明现有 MVP 的"解析 → 滚榜 → 主持词"文本链路已经打通。

### 失败一例

输入文件 `test_invalid.json`：

```json
{
  "teams": 123
}
```

实际执行命令：

```bash
python main.py test_invalid.json --roll
```

`teams` 类型错误（是数字 123，不是要求的列表），程序在 `parse_leaderboard_file` 阶段校验并抛出真实异常：

```text
ValueError: 排行榜 JSON 的 teams 必须是列表，实际为 int
```

完整真实终端输出（含 traceback）见 `reports/day03_failure_example.txt`。解析失败后程序在解析阶段终止，不进入 `roll`、`script` 和 `tts`，避免错误数据继续传播。

其余异常情况（非法 JSON、顶层非对象、队伍超上限、`teams` 缺失、队伍字段缺失等）的真实执行结果统一记录在 `reports/day03_parser_failure_log.txt`，正文不再逐一展开。

## 五、临时假实现

当前 MVP 主路径已经可以运行，但为了后续增强真实滚榜，仍保留一处明确的临时实现。

### `roll` 的当前实现

目前 `roll.reveal_order` 主要根据已经计算完成的最终排名，按照：

```text
最后一名
→ ...
→ 第一名
```

生成揭晓顺序。

该实现可以满足第 1 天确定的 MVP，但是它并不模拟真正滚榜中的：

```text
封榜
→ 隐藏提交
→ 提交解冻
→ 成绩重新计算
→ 排名变化
→ 重新揭晓
```

因此这里将其明确记录为：

> **MVP 可运行实现，但后续真实滚榜增强的临时版本。**

计划从第 4 天开始，在不影响现有 MVP 的前提下逐步增加简化 ICPC 风格的成绩计算和排名变化模拟。

这一增强不改变第 1 天"最终可交付的最小功能集"，而是作为本项目后续的特色功能，用于提升滚榜真实性和现场表现。

### `script` 的当前实现

主持词目前采用规则模板生成，不依赖在线大模型。

该方案属于正式 MVP 实现，不是等待替换的假实现。

后续增强方向不是简单接入 API，而是根据滚榜事件选择不同主持情境，例如：

```text
普通揭晓
排名不变
排名上升
反超
大幅跃升
进入前三
进入前二
冠军揭晓
```

使主持词能够随着比赛状态变化，而不是从头到尾播放一份固定台本。

## 八、问题、计划与 AI 沟通

### 不成功的沟通

第一次让 AI 直接设计完整的智能主持人系统时，容易得到包含 Web、数据库、账号和在线大模型等内容的大型方案，其中很多功能与本项目的核心滚榜流程没有直接关系。

另外，在前期方案讨论中曾把"封榜解冻、罚时重算"直接定义成后续必做功能，这与第 1 天确定的 MVP 边界存在冲突。

### 处理方式

重新将项目范围分成两层：

```text
MVP：
JSON → 排名 → 主持词 → TTS

特色增强：
比赛数据 → 滚榜状态变化 → 事件识别 → 情境化主持 → TTS
```

这样既保证原来的 MVP 能按计划交付，又能够在后续实践中围绕"真正的滚榜主持"增加项目特色。

### 比较有效的沟通

要求 AI：

1. 只围绕主路径定义数据对象；
2. 每个关键接口必须提供成功例和失败例；
3. 所有"已完成"必须以实际代码和运行结果为准；
4. 对增强功能明确区分"当前实现"和"后续计划"，不能提前写成已经完成；
5. 不为了体现 AI 而强行引入在线 API。

采用这种方式后，项目的基础 MVP 和后续特色增强可以保持连续。
